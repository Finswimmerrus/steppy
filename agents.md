# Steppy — handoff-ТЗ для AI-агентов и команды разработки

## Статус документа

Этот файл — самостоятельный источник продуктового и технического контекста проекта Steppy. Он фиксирует только подтверждённые решения и явно отделяет их от предположений. Любой пункт с пометкой **TBD** требует отдельного продуктового, юридического, финансового, дизайнерского или технического решения.

Рабочее название продукта — **Steppy**. Продукт вдохновлён механикой StepBet, но не должен копировать чужие бренд, интерфейс, тексты или защищённые материалы.

## Краткая продуктовая концепция

Steppy — мобильное приложение персональных шаговых челленджей. Пользователь подключает источник данных о шагах, получает персональные дневные цели, сформированные на основе его истории активности, вступает в челлендж на несколько настраиваемых недель и должен выполнять требования каждого дня. В денежном B2C-режиме участники формируют общий банк; невыполнение дневного требования после предусмотренного окна синхронизации приводит к математически однозначному выбыванию. В корпоративном режиме тот же игровой движок используется без реальных денежных ставок — с внутренними баллами, наградами и white-label-настройками организации.

Главная ценность — не абстрактный шагомер, а понятная игра на регулярность: персональная достижимая нагрузка, ежедневный риск выбывания, прозрачный прогресс и социальная мотивация.

## Product principles

1. **Персональность вместо единого норматива.** Цели должны учитывать собственную историю пользователя, а не сравнивать всех по одной абсолютной планке.
2. **Прозрачная математика.** До вступления пользователь видит длительность, календарь, типы дней, свои цели, условия выбывания, финансовые правила и дедлайн синхронизации.
3. **Сервер решает исход.** Клиент отображает состояние, но не определяет факт выполнения, выбывания, состав победителей или денежный результат.
4. **Одинаковые правила для одинаковых входных данных.** Расчёты должны быть детерминированными, версионируемыми и пригодными для аудита.
5. **Данные могут приходить с задержкой.** UX и backend обязаны различать «не выполнено» и «ещё не синхронизировано».
6. **Мотивация без токсичности.** Социальные и брендовые коммуникации поддерживают дисциплину, но не стыдят пользователя и не обещают медицинский результат.
7. **Privacy by design.** Запрашивать минимум health-данных, ясно объяснять их применение и не раскрывать личную активность сверх выбранной пользователем видимости.
8. **Один игровой движок, несколько оболочек.** B2C и corporate/white-label используют общие сущности и правила, а деньги, баллы, оформление и доступ конфигурируются.

## Confirmed decisions

- Рабочее имя: **Steppy**.
- Основной формат: персональные шаговые челленджи на настраиваемое число недель.
- До основного периода может быть включён необязательный warm-up.
- Календарь использует три типа дней: **Активный**, **Усиленный**, **Свободный**.
- Цели персональны и фиксируются snapshot-ом для конкретного участия/челленджа.
- Проверка выполнения и выбывание происходят ежедневно по формальному правилу.
- После календарного дня предусмотрено 12-часовое окно для поступления/синхронизации шагов.
- Timezone и точная day-boundary-семантика ещё не утверждены.
- В денежном режиме существует общий банк; если победителей `W = 0`, деньги полностью возвращаются участникам.
- Corporate/white-label использует тот же игровой движок, но внутренние баллы вместо реальных денежных ставок.
- Мобильные источники шагов: Apple HealthKit и Android Health Connect.
- Сервер — source of truth для результата челленджа.
- Нужны anti-fraud-механизмы, API/SDK, SSO и модель Organization.
- Социальный контент является частью продукта.

## Механика челленджа

### Периоды

- **Warm-up** — необязательный подготовительный период. Его длительность, влияние на цели и наличие санкций — **TBD**. По умолчанию нельзя считать, что warm-up влияет на денежный исход.
- **Основной период** — настраиваемое целое число недель. Допустимые минимум/максимум и готовые пресеты — **TBD**.
- Для каждого календарного дня заранее существует тип дня и требуемая цель.

### Типы дней

- **Активный день** — пользователь должен набрать персональную активную цель.
- **Усиленный день** — пользователь должен набрать более высокую персональную цель. Формула/множитель относительно активной цели — **TBD**.
- **Свободный день** — обязательной цели для сохранения участия нет; шаги могут продолжать учитываться для статистики и социального контента. Точные эффекты свободного дня — **TBD**.

### Персональные цели и snapshot

Цели рассчитываются из допустимой истории шагов пользователя по версионируемому алгоритму. Точное окно истории, статистическая формула, округление, минимумы/максимумы, обработка пропусков и выбросов — **TBD**.

Перед подтверждением участия создаётся неизменяемый **goal snapshot**, содержащий как минимум:

- рассчитанные цели по типам дня;
- версию алгоритма;
- данные/агрегаты, достаточные для объяснения расчёта без избыточного хранения health-данных;
- время расчёта;
- timezone-контекст, когда он будет утверждён;
- применённые ограничения и округление.

Цели активного участия не должны незаметно меняться из-за новой активности или изменения алгоритма. Пересчёт и исключительные миграции — только по явно утверждённому правилу и с аудитом.

### Ежедневное математическое выбывание

Для обязательного дня `d`:

- `S(u,d)` — принятое сервером валидное число шагов пользователя `u` за день `d`;
- `G(u,d)` — цель из snapshot пользователя для типа дня `d`;
- `deadline(d)` — конец дня плюс 12 часов на синхронизацию по утверждённым timezone/day-boundary-правилам.

После `deadline(d)`:

- если `S(u,d) >= G(u,d)`, день выполнен;
- если `S(u,d) < G(u,d)`, пользователь выбывает;
- для Свободного дня это сравнение не вызывает выбывание.

До дедлайна недостаток данных отображается как ожидающий синхронизации, а не окончательное поражение. Поведение при позднем импорте, исправлении данных, сбое провайдера и апелляции — **TBD**. Решение о выбывании должно сохранять входные значения, версию правила и timestamp.

## Financial rules

- Реальные деньги допустимы только в consumer/B2C-режиме и только после юридической, платёжной, налоговой и географической проверки — **TBD**.
- Взносы участников формируют банк конкретного челленджа.
- `W` — число победителей после финального расчёта.
- Если `W = 0`, действует **полный возврат**: каждому участнику возвращается внесённая им сумма. Комиссии, курсовые разницы и источник покрытия невозвратных платёжных комиссий — **TBD**; термин «полный возврат» должен быть реализован и раскрыт пользователю буквально.
- Если `W > 0`, формула распределения банка, комиссии платформы, округление, остатки, налоги и сроки выплат — **TBD**. Не предполагать автоматически равное деление, пока это не утверждено.
- Нужны отдельные состояния ledger: initiated, authorized/paid, held, refundable, refund_pending, refunded, payout_pending, paid_out, failed, disputed (точный набор **TBD**).
- Финансовые записи должны быть идемпотентными, аудируемыми и не изменяться прямым редактированием; корректировки проводятся отдельными операциями.
- Нельзя показывать гарантированный выигрыш или трактовать Steppy как инвестиционный продукт.

## Data/sync

### Источники

- iOS: **HealthKit**.
- Android: **Health Connect**.
- Поддержка часов, производителей и иных источников происходит через эти платформы или будущие интеграции — **TBD**.

### Принципы синхронизации

- Клиент получает разрешение пользователя и загружает минимально необходимые агрегаты/семплы.
- Импорт должен быть повторяемым и идемпотентным: повторная отправка одних данных не увеличивает итог.
- Сервер нормализует данные, дедуплицирует их, применяет anti-fraud-проверки и формирует канонический дневной итог.
- Нужно хранить provenance: источник, устройство/тип записи, время начала/окончания, время получения и идентификатор импорта в доступном провайдером объёме.
- UI показывает время последней успешной синхронизации, покрытый период, предварительный/финальный статус и понятное действие «Синхронизировать».
- Локальное число шагов может отличаться от серверного принятого итога; интерфейс должен объяснять статус, а не молча подменять число.
- Повторная авторизация, отзыв разрешений, смена телефона, переустановка, отсутствие фоновой синхронизации и offline-режим должны иметь явные состояния.

### 12-часовое окно и календарь

Подтверждено только наличие **12 часов после дня** для доставки данных. Следующее требует решения:

- timezone челленджа, организации или пользователя;
- фиксация timezone при вступлении или следование за поездками;
- DST и переходы времени;
- точный момент начала/конца дня;
- можно ли менять timezone во время челленджа;
- обработка шагов с пересекающими границу интервалами;
- разрешённость и порядок позднего перерасчёта.

До решения нельзя реализовывать необратимые финансовые исходы на основании неформализованной локальной даты.

### Server source of truth

Сервер хранит канонические агрегаты, состояние участия, результаты дневных проверок, факт выбывания, победителей, ledger и версии правил. Клиентские вычисления допустимы только как предварительный UX и никогда не являются основанием для выплаты/выбывания.

### Anti-fraud

Нужна риск-система, а не одно эвристическое правило. Минимальные направления:

- дедупликация перекрывающихся источников и повторных импортов;
- выявление невозможной скорости/частоты и аномальных скачков;
- признаки ручного ввода, синтетических данных, эмуляторов, root/jailbreak и смены устройства — в пределах возможностей платформ и закона;
- анализ поздних массовых правок и несогласованности источников;
- risk score, очередь ручной проверки, причина решения и аудит;
- мягкие промежуточные состояния `under_review` вместо автоматического наказания при неоднозначности;
- процесс апелляции, сроки и политика хранения данных — **TBD**.

Anti-fraud не должен раскрывать злоумышленнику точные пороги и не должен автоматически дискриминировать нормальные паттерны доступности или здоровья.

## Основные экраны и состояния

### Общие/B2C

1. Онбординг: ценность продукта, разрешения, privacy, подключение HealthKit/Health Connect.
2. Главная: активный челлендж, сегодняшняя цель, прогресс, тип дня, статус синхронизации, дедлайн, серия/календарь.
3. Каталог/описание челленджей: длительность, warm-up, расписание типов дней, входной взнос или режим без денег, правила.
4. Персональный расчёт: история/достаточность данных, активная и усиленная цели, объяснение snapshot.
5. Вступление и подтверждение: правила выбывания, сумма, согласия, итоговые цели.
6. Активный челлендж: календарь недель, дневные результаты, участники/социальная лента, банк или баллы.
7. Дневной detail: принятые шаги, цель, источник, последняя синхронизация, предварительный/финальный статус.
8. Результат дня: выполнено; ожидается синхронизация; недостаточно шагов до дедлайна; выбывание; проверка anti-fraud; техническая задержка.
9. Финал: победа, проигрыш/выбывание, `W = 0` и возврат, выплата/награда, share card.
10. Кошелёк/операции для денежного режима: взнос, возврат, выплата, ошибки и поддержка.
11. Профиль и настройки: health-подключение, уведомления, privacy, timezone (после решения), история челленджей.
12. Поддержка/апелляция: проблема синхронизации, спорные данные, финансовый вопрос.

### Обязательные сквозные состояния

Loading, empty, offline, permission denied, health source unavailable, insufficient history, sync in progress, sync stale, pending deadline, completed, failed, eliminated, under review, challenged/appealed, refunded, payout pending, service incident. Для каждого должны быть понятны причина, последствия и следующее действие.

## Frontend handoff

### Зона ответственности

- Нативная интеграция с HealthKit и Health Connect, включая permissions и фоновые ограничения.
- Отображение серверных целей, календаря, статусов, результатов и финансовых данных без самостоятельного вынесения окончательного решения.
- Надёжная очередь синхронизации с retry, idempotency key и видимым пользователю статусом.
- Онбординг, вступление, подтверждение snapshot и информированное согласие.
- Push/in-app-уведомления о цели, риске, окончании дня, необходимости синхронизации, результате и награде.
- Social/share UX, доступность, локализация и white-label theming.
- Телеметрия продуктовых событий без утечки health- и финансовых данных.

### Контрактные ожидания

- Сервер возвращает явные статусы и timestamp-ы, а не требует выводить их из косвенных полей.
- Все денежные величины передаются в minor units + currency; даты — ISO 8601 с offset/zone context.
- Клиент должен переживать устаревшие ответы, повторные запросы, частичную синхронизацию и смену статуса после background refresh.
- Feature flags и rule/config versions должны приходить с backend.
- UI-компоненты строить так, чтобы B2C и corporate различались конфигурацией, темой и доступными модулями, а не двумя полностью отдельными приложениями, если исследование не докажет обратное.

## Backend handoff

### Зона ответственности

- Identity, authentication, user profile и consent.
- Organization/tenant, membership, роли, SSO и white-label-конфигурация.
- Каталог и конфигурация челленджей; enrollment; goal calculation и immutable snapshot.
- Приём, нормализация, дедупликация и агрегация шагов.
- Версионируемый rules engine типов дня и ежедневной проверки.
- Планировщик финализации после sync window; идемпотентное выбывание.
- Anti-fraud/risk review и аудит.
- Денежный ledger, refunds/payouts и интеграция платёжного провайдера — после правового решения.
- Внутренние баллы/награды corporate-режима.
- Social content, moderation hooks и notifications.
- Admin/support-инструменты, observability, incident handling и экспорт аудита.

### API/SDK

Нужен версионируемый API для first-party клиентов и corporate-интеграций. Конкретный REST/GraphQL/gRPC-стек — **TBD**. Требования:

- OAuth/OIDC-совместимая авторизация; SSO для организаций (SAML и/или OIDC — **TBD**);
- tenant isolation и role-based access;
- idempotency для sync, enrollment и денег;
- cursor pagination, rate limiting, correlation/request IDs;
- webhooks для корпоративных событий с подписью, retry и replay protection;
- SDK или документированный integration kit для SSO, enrollment, баллов, результатов и branding;
- backward compatibility и политика deprecation;
- sandbox/test organization и синтетические health-данные.

## Design handoff

### Продуктовый дизайн

- Главный фокус экрана активного дня: «сколько сделано / сколько нужно / сколько времени осталось / синхронизированы ли данные».
- Визуально различать предварительный прогресс и финальный серверный результат.
- До оплаты или вступления показать персональные цели и существенные правила без скрытия в длинных условиях.
- Проработать все состояния permissions, sync, elimination, review, refund и payout.
- Не использовать стыдящие формулировки; поражение объяснять спокойно и математически.
- Денежный и корпоративный режимы должны быть различимы, но сохранять общую продуктовую грамматику.

### Design deliverables

- user flows B2C и corporate;
- информационная архитектура;
- wireframes и high-fidelity макеты основных экранов/состояний;
- дизайн-система и токены темизации;
- motion/feedback для прогресса, выполнения, риска и финала;
- accessibility: contrast, Dynamic Type/масштабирование, screen reader labels, reduced motion;
- Steppy Brand Kit и character sheet маскота.

## Corporate/white-label

Corporate-режим работает поверх того же challenge/rules engine. Отличия:

- tenant `Organization` с собственными администраторами, участниками и настройками;
- логотип, цвета, тексты, домен/ссылки и доступные награды настраиваются в пределах дизайн-системы;
- вход через invite и/или корпоративный SSO;
- вместо денежного банка — внутренние баллы, бейджи, призы или benefits; модель их обмена — **TBD**;
- организация создаёт кампании из разрешённых шаблонов или конфигурации;
- возможны команды, департаменты и групповые рейтинги — **TBD**;
- HR/admin dashboard, агрегированная аналитика и выгрузки — **TBD**;
- индивидуальные health-данные не должны становиться доступны работодателю по умолчанию. Видимость, пороги анонимизации, consent, retention и DPA — **TBD** и требуют legal/privacy review;
- API/SDK/webhooks позволяют связать Steppy с HRIS, rewards и внутренними порталами — конкретные интеграции **TBD**.

## Социальный контент

Предусмотреть:

- ленту событий челленджа (вступление, выполненный день, milestone, финал) с privacy-настройками;
- реакции/поддержку, share cards и командные сообщения;
- рейтинги только там, где они не разрушают принцип персональных целей;
- маскота как ведущего, coach и носителя системных сообщений;

## Terminology

- **Steppy** — рабочее имя продукта и бренда.
- **Челлендж** — ограниченная по времени игра с расписанием правил.
- **Участие / Enrollment** — связь пользователя с конкретным челленджем и его зафиксированными условиями.
- **Warm-up** — необязательный подготовительный период до основного челленджа.
- **Активный день** — обязательный день с персональной базовой целью.
- **Усиленный день** — обязательный день с повышенной персональной целью.
- **Свободный день** — день без условия выбывания по шагам.
- **Goal snapshot** — неизменяемая фиксация персональных целей и версии их расчёта для участия.
- **Sync window** — 12 часов после дня для доставки данных до финальной проверки.
- **Выбывание / Elimination** — необратимый игровой статус после финального серверного решения; возможный appeal/reversal — **TBD**.
- **Победитель** — невыбывший участник, удовлетворивший финальным правилам челленджа.
- **`W`** — число победителей.
- **Банк** — денежная масса конкретного B2C-челленджа, учитываемая в ledger.
- **Баллы** — неденежная корпоративная единица; конвертируемость и юридический статус — **TBD**.
- **Organization** — tenant корпоративного клиента.
- **Server source of truth** — серверное состояние, определяющее официальный результат.

## Implementation status — Android prototype, 2026-10-03

Этот раздел фиксирует состояние реализации, а не новые продуктовые решения. Наличие экрана или демонстрационного значения не переводит соответствующий пункт из **TBD** в Confirmed decisions.

### Реализовано и проверено

- Создан нативный Android-проект `ru.finswimmer.steppy` на Kotlin и Jetpack Compose, `minSdk 28`, `targetSdk 35`, `compileSdk 36`.
- Настроена воспроизводимая Gradle-сборка; `assembleDebug` успешно формирует APK.
- Проект установлен и запущен на эмуляторе Pixel 7 / Android 15; холодный старт проверен без crash-записей.
- Реализован onboarding с объяснением минимального доступа к health-данным и возможностью открыть demo-режим.
- Интегрирован Android Health Connect: проверка доступности, запрос разрешения только на чтение шагов, проверка выданного разрешения и чтение агрегата шагов за текущий день.
- Реализован экран «Сегодня»: динамическая текущая дата, горизонтальная текущая неделя, тип дня, персональная demo-цель, прогресс, sync status и 12-часовое окно как информационный текст.
- Нижняя навигация содержит четыре раздела: «Сегодня», «Мои игры», «Поиск», «Создать».
- «Мои игры» показывает демонстрационные активные и завершённые челленджи.
- «Поиск» фильтрует локальный список открытых демонстрационных челленджей.
- «Создать» доступен любому пользователю и создаёт только локальный UI-черновик с названием и длительностью; публикации и серверной записи пока нет.
- Верхняя иконка маскота на экране «Сегодня» открывает профиль; в профиле доступны входы в Health Connect, notifications, privacy и support, пока без полноценных downstream-flow.
- В приложение добавлен рабочий PNG-маскот: жёлтый округлый персонаж, белая повязка с `S`, кроссовки. Это временный проектный ассет, а не утверждённый Brand Kit; после получения исходного визуального борда его нужно сверить или заменить.
- Денежные операции и необратимое клиентское выбывание отсутствуют. UI явно обозначает тестовый режим.

### Используемые демонстрационные допущения

- Числа шагов, цели, участники, сроки, названия челленджей и состояние календаря в demo repository являются fixtures для проверки интерфейса.

## Acceptance criteria for MVP

MVP можно считать функционально принятым, если:

1. Пользователь на поддерживаемых iOS/Android может зарегистрироваться, дать consent и подключить HealthKit/Health Connect.
2. Система проверяет достаточность истории и создаёт версионируемый goal snapshot, который пользователь видит до вступления.
3. Администратор/конфигурация создаёт челлендж на настраиваемое число недель, с optional warm-up и календарём трёх типов дней.
4. Пользователь вступает, видит сегодняшнюю цель, прогресс, тип дня, последний sync и дедлайн.
5. Повторная/частичная синхронизация идемпотентна; сервер формирует канонический дневной итог.
6. До дедлайна состояние корректно помечается pending; после дедлайна rules engine детерминированно фиксирует pass/elimination и сохраняет аудит входных данных.
7. Свободный день не приводит к выбыванию по шагам; Активный и Усиленный сравниваются с соответствующей целью snapshot.
8. Клиент не может самостоятельно изменить официальный результат; повторный job не создаёт вторичное выбывание или двойную финансовую операцию.
9. Пользователь получает понятные уведомления/экраны для успеха, риска синхронизации, выбывания, review и финала.
10. Реализован минимальный anti-fraud pipeline с provenance, дедупликацией, risk flag и audit trail; спорный результат может быть помещён `under_review`.
11. Для денежного MVP (только если legal/payment scope утверждён) ledger корректно учитывает взносы и при `W = 0` запускает полный возврат без двойной обработки. Сценарий `W > 0` принимается только после утверждения формулы.
12. Corporate MVP создаёт Organization, применяет тему, допускает SSO/invite, запускает тот же тип челленджа с баллами без денежных транзакций и изолирует tenant data.
13. Базовый социальный event feed/share card соблюдает настройки приватности и имеет путь модерации для UGC, если UGC включён.
14. Есть admin/support view для аудита sync, evaluation, risk и финансового/балльного состояния без прямого редактирования истории.
15. Покрыты тестами граничные случаи: повторный импорт, данные ровно на цели, данные у дедлайна, `W = 0`, повторный refund job, отозванные permissions, offline/retry и tenant isolation.
16. Утверждённая timezone/day-boundary-спецификация существует до запуска реального ежедневного выбывания и денег. Пока её нет, MVP может работать только в безопасном тестовом режиме без необратимых исходов.
